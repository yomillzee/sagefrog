# Architecture Review: Sagefrog Marketing Analytics Platform

_Reviewed: June 15, 2026. Technical Debt and Areas of Risk rewritten against
the tree on 7 September 2026; the descriptive sections above them were checked
at the same time._

---

## Purpose of the Application

Sagefrog is a **multi-platform marketing analytics dashboard and API service** built for a digital marketing agency. Its primary function is aggregating paid media performance data from Google Ads, LinkedIn, Meta, GA4/BigQuery, and Indeed into a single unified view, with Penn Community Bank as the primary (and currently most built-out) client dashboard.

The system serves two audiences:

1. **Agency staff (admins)**: manage dashboards, users, OAuth connections, business line classification rules, and client-facing documents
2. **Clients**: read-only view of their own marketing performance via a branded dashboard

A secondary capability is a **ChatGPT Custom Action integration** — the API exposes OpenAPI schemas so a GPT can query live performance data on behalf of agency users.

## Frontend Architecture

There is no client-side frontend framework. All UI is **server-side HTML rendered by FastAPI** and returned as `text/html` responses. JavaScript on the page is minimal and inlined directly in `<script>` tags within the rendered HTML.

### Rendering Layer

The dashboard UI is generated by a suite of Python renderer modules under `railway/app/dashboard/renderers/`. **Every client renders through one master template**, `bigquery_dashboard_renderer.py` (`render_bigquery_dashboard_page`); there are no per-client dashboard renderers, and per-client differences are driven by `client_dashboard_config`, not by branching on a client's name. See `railway/app/dashboard/ARCHITECTURE.md`.

| Module | Responsibility |
|---|---|
| `bigquery_dashboard_renderer.py` | **The master dashboard template** — every client's dashboard |
| `base_layout.py` | Topbar, session account chip, refresh toolbar, shell pages, canonical sidebar nav |
| `cards_renderer.py` | Summary cards, hero metrics row, budget pacing panel |
| `tables_renderer.py` | Platform drill-down tables, GA4 rows |
| `bigquery_settings_renderer.py` | Client settings page (accounts, mart routing, KPI, segment filters) |
| `files_renderer.py` | File browser, time tracking page, insight document library |

### Dashboard Routes

```
GET  /dashboard/{client_slug}              → full HTML dashboard
GET  /dashboard/{client_slug}/settings     → settings page
GET  /dashboard/{client_slug}/files        → file browser
POST /dashboard/{client_slug}/refresh      → trigger data refresh (JSON)
GET  /dashboard/{client_slug}.json         → raw data export
```

### State Management

- **Server-side rendering only**: every GET request re-renders the full HTML page
- **Session cookies**: `eos_session` cookie (14-day max age, signed with `itsdangerous` via Starlette's `SessionMiddleware`)
- **Client-side JS**: date range filtering, chart rendering, and campaign drill-down are handled by vanilla JavaScript embedded in the rendered page
- No React, Vue, Alpine, or any JS framework

### UI Libraries / Styling

All CSS is custom and inline. There is no CSS framework (no Tailwind, Bootstrap, etc.). No component library. Charting is done with inline JavaScript.

## Database Architecture

### Engine

PostgreSQL, accessed with `psycopg` v3 (synchronous driver). Connection string injected by Railway's Postgres plugin as `DATABASE_URL`. No ORM — all queries are raw SQL via `psycopg.connect()`.

### Schema Management

Each module calls its own `ensure_schema()` on first use, which runs `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` statements. There is no migrations framework (no Alembic, no Flyway).

### Tables

| Table | Purpose |
|---|---|
| `web_users` | Browser login accounts (email, bcrypt hash, role, client_slug) |
| `api_cache` | SHA256-keyed response cache for all platform API calls (~1 hour TTL) |
| `metrics_daily` | Daily aggregated paid media metrics (spend, clicks, impressions, conversions) |
| `oauth_credentials` | Encrypted refresh/access tokens for Google Ads, LinkedIn, Meta, Harvest |
| `dashboard_snapshots` | JSONB snapshots of refreshed dashboard data per client per date |
| `audit_events` | Append-only audit trail (login, user management, etc.) |
| `client_dashboard_config` | Per-client configuration JSON (account IDs, budget, labels) |
| `dashboard_registry` | Admin-created client dashboard registry |
| `client_business_line_rules` | Keyword-based campaign classification rules per client |
| `client_insight_documents` | Binary file storage (PDF, DOCX) as `BYTEA` |
| `admin_dev_notes` | Internal agency notes (title, body, category) |
| `login_rate_buckets` | Failed login tracking for IP/email rate limiting |

### Key Design Decisions

- **`metrics_daily`**: The central time-series fact table. Unique on `(source, account_id, metric_date)` with upsert semantics. Covers Google, LinkedIn, Meta, GA4.
- **`api_cache`**: Platform API responses are cached to reduce third-party API calls and rate limit exposure. Cache key is SHA256 of `source + canonical_json(payload)`.
- **`oauth_credentials`**: Tokens are encrypted at rest using Fernet symmetric encryption. The key is derived (SHA256) from `OAUTH_TOKEN_ENCRYPTION_KEY` → `AUTH_SESSION_SECRET` → `CRON_SECRET` → `API_KEY`.
- **`client_insight_documents`**: Files stored as PostgreSQL `BYTEA`, not in an object store.

## Authentication Flow

### API Key Authentication (Stateless)

Used by ChatGPT integrations and any external callers hitting `/google-ads/*`, `/linkedin/*`, `/meta/*`, `/ga4/*`, `/indeed/*`, `/warehouse/*`.

1. Caller sends `Authorization: Bearer <API_KEY>` or `X-API-Key: <API_KEY>`
2. `security.py:require_api_key()` compares token to `os.getenv("API_KEY")`
3. If `API_KEY` is unset, the check passes — endpoints are **open** (documented as local dev behavior)
4. No per-user identity; single shared secret

### Browser Session Authentication (Stateful)

Used by the dashboard UI and admin pages.

1. User submits login form (`POST /login`)
2. `login_rate_limit.check_login_allowed()` checks IP and email buckets in Postgres — blocks after N failures (default 5) within a 15-minute window
3. `web_users.authenticate()` queries `web_users` table, verifies bcrypt hash
4. On success: `request.session["user_id"] = user.id` (stored in the signed `eos_session` cookie via Starlette SessionMiddleware)
5. `audit_log` records login success/failure
6. On subsequent requests: `web_auth.get_current_user()` reads `user_id` from session, loads user from Postgres
7. Role check: `admin` can access any dashboard; `client` can only access dashboards matching their `client_slug`
8. Session cookie: 14-day max age, `SameSite=Lax`, HTTPS-only when `RAILWAY_ENVIRONMENT` or `AUTH_SESSION_HTTPS_ONLY` is set

### Legacy `?key=` share link retired

Dashboards were previously also reachable via `/dashboard/{slug}?key=<secret>` — a single shared, non-expiring, non-audited passwordless link keyed on `DASHBOARD_SECRET`. This mechanism has been **removed entirely**: `authenticate_dashboard` / `authenticate_dashboard_api` are session-only, the `verify_dashboard_key` / `configured_dashboard_secret` / `legacy_dashboard_key_ok` helpers and all route `key` parameters are gone, and `DASHBOARD_SECRET` is no longer read. To grant someone dashboard access, create a `client`-role account scoped to their `client_slug` (per-person, individually revocable, recorded in the audit log). Endpoints that also accept the external `API_KEY` (ChatGPT / API callers) are unaffected.

### OAuth Token Management

Used to authorize the service to call third-party marketing APIs on behalf of the agency.

1. Admin navigates to Settings → clicks "Connect {Platform}"
2. `GET /oauth/{platform}/connect` generates a PKCE state token, stores it in the session, and redirects to the OAuth provider's authorization URL
3. Provider redirects to `GET /oauth/{platform}/callback?code=...&state=...`
4. State is verified; code is exchanged for tokens via `httpx`
5. Tokens are encrypted with Fernet and stored in `oauth_credentials` table
6. On each API call: service calls `oauth_store.get_refresh_token(platform)`, decrypts, and uses the token to obtain a fresh access token from the provider

**Fallback**: Google Ads also supports `GOOGLE_ADS_REFRESH_TOKEN` env var if no Postgres token is stored.

### Cron Authentication

`POST /internal/sync-penn` requires `X-Cron-Secret: <CRON_SECRET>` header — exact string match, no fallback.

## Data Ingestion Flow

### Cron Sync (Scheduled)

A separate Railway service (`railway/cron-sync-penn/`) runs on a user-configured cron schedule:

```
cron worker → POST /internal/sync-penn?date_range=LAST_30_DAYS
           → (main service) refresh_penn()
           → sync all platform warehouses
           → update dashboard_snapshots
```

The cron worker is a minimal Python script (`run_sync_penn.py`) that makes a single HTTP POST call to the main service using `urllib`. The cron schedule is configured in Railway's project settings, not in the code.

### On-Demand Warehouse Sync (API)

Each platform exposes a warehouse sync endpoint:

```
POST /google-ads/warehouse/sync  { customer_id, date_range }
POST /linkedin/warehouse/sync    { account_id, date_range }
POST /meta/warehouse/sync        { account_id, date_range }
POST /ga4/warehouse/sync         { date_range, client_key, bq_project_id, bq_dataset_id }
```

Sync path for paid media (Google, LinkedIn, Meta):
1. Call platform API for daily metrics in the requested date range
2. `warehouse.upsert_metrics_daily_batch()` — upsert rows into `metrics_daily`

Sync path for GA4:
1. Run BigQuery SQL against the client's GA4 events export dataset
2. Parse events into daily aggregates
3. Upsert into `metrics_daily` under source `ga4`

### Dashboard Refresh

```
POST /dashboard/{slug}/refresh?force=1
  → refresh_service.refresh_penn()
  → pull live data from all platform APIs
  → sync warehouse for current month
  → snapshot_metrics_service: compute totals, breakdowns, budget pacing
  → dashboard_snapshots.save() → upserts to dashboard_snapshots table
```

A refresh cooldown (minimum 60 seconds between refreshes) is enforced via the `dashboard_snapshots` table.

### API Response Cache

All platform API calls check `db_cache.get_cached()` before hitting the live API. Cache key = `SHA256(source + canonical_JSON(payload))`. Default TTL = 3600 seconds, configurable via `CACHE_TTL_SECONDS`. Cache is stored in the `api_cache` Postgres table. The write-through goes
through `db_cache.put_cached_best_effort`, which logs a failure rather than
letting a cache problem turn a good response into a 500.

## Third-Party Integrations

### Google Ads

- **Client**: `google-ads` Python library (OAuth2 service account)
- **Auth**: OAuth refresh token (Postgres `oauth_credentials` or `GOOGLE_ADS_REFRESH_TOKEN` env)
- **Capabilities**: GAQL queries, account listing, account metadata, YouTube video asset discovery, daily metric backfill
- **Error handling**: Detects `invalid_grant`, returns safe credential hints

### LinkedIn Marketing API

- **Client**: `httpx` (REST, JSON)
- **API version**: Configurable via `LINKEDIN_VERSION` (default `202604`); fallback chain for version mismatches
- **Auth**: OAuth refresh token (Postgres or `LINKEDIN_REFRESH_TOKEN` env)
- **Capabilities**: Account listing, campaign/campaign-group/creative performance, video creative URLs, daily metric backfill

### Meta (Facebook) Ads

- **Client**: `httpx` (Graph API, REST)
- **API version**: Configurable via `META_API_VERSION` (default `v21.0`)
- **Auth**: System user access token via OAuth (`META_APP_ID`, `META_APP_SECRET`, `META_BUSINESS_ID`)
- **Capabilities**: Business Manager account listing, campaign/ad set insights, video creative assets, daily metric backfill
- **Requirements**: System user must have `ads_read` and `business_management` scopes

### GA4 / BigQuery

- **Client**: `google-cloud-bigquery` Python library
- **Auth**: GCP service account JSON (base64-encoded in env; per-client or global)
- **Capabilities**: Raw BigQuery SQL queries against GA4 events export tables, event parsing into daily aggregates
- **Multi-project**: `GA4_CLIENTS` JSON registry allows each client to have their own BQ project, dataset, and service account (`GCP_CREDS_*_BASE64`)
- **Credential parsing**: Handles raw JSON, double-encoded JSON, and base64 with automatic format detection (`ga4_credentials.py`)

### Indeed Job Postings

- **Client**: `httpx` (REST)
- **Auth**: Client credentials OAuth (`INDEED_CLIENT_ID`, `INDEED_CLIENT_SECRET`)
- **Capabilities**: List job postings with registration counts, posting details, registration analytics by job title
- **Status**: Recently added integration; limited validation

### Harvest (Time Tracking)

- **Client**: `httpx`
- **Auth**: OAuth refresh token (`HARVEST_CLIENT_ID`, `HARVEST_CLIENT_SECRET`)
- **Capabilities**: Time tracking data retrieval (used in the Files/time tracking page)
- **Status**: Minimal implementation; primarily for Penn internal use

### ChatGPT Custom Actions

- `GET /openapi-gpt.json` returns a dynamically generated OpenAPI 3.1 schema
- Three schema variants exist: full-agency, Penn-only, minimal
- Enables a Custom GPT to call live API endpoints using the shared `API_KEY`

## Deployment Architecture

### Railway Services

The application runs on [Railway](https://railway.app) as two services within one project:

```
Railway Project: sagefrog
  ├── Service: app                        (main FastAPI server)
  │     root: railway/app/
  │     start: uvicorn main:app --host 0.0.0.0 --port $PORT
  │     health: GET /health
  │     plugins: PostgreSQL (auto-injects DATABASE_URL)
  │
  └── Service: cron-sync-penn             (periodic sync worker)
        root: railway/cron-sync-penn/
        start: python run_sync_penn.py
        runs on user-defined Railway cron schedule
        calls: POST /internal/sync-penn on app service
```

### Startup Behavior

On `main.py` startup:
1. Load `.env` (local dev) or Railway-injected environment
2. Attach `SessionMiddleware` (requires session secret)
3. Mount static files at `/static`
4. Register dashboard routes (`register_dashboard_routes(app)`)
5. Each module self-initializes its DB schema on first request via `ensure_schema()`
6. Bootstrap admin user if `AUTH_BOOTSTRAP_ADMIN_EMAIL` is set and no admin exists

### CI/CD

There is no CI/CD pipeline configuration (no `.github/workflows/`, no `Dockerfile`, no `vercel.json`). Deployments are presumably triggered by Railway's GitHub integration (git push to main triggers redeploy).

### Local Development

```bash
cd railway/app
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env   # populate credentials
uvicorn main:app --reload
# → http://127.0.0.1:8000

```

## Technical Debt

_This section was rewritten on 7 September 2026 against the checkout at that
date. The version before it was three months old and had become actively
misleading: it named twelve debts, nine of which were fixed or had never been
accurate, so anyone working from it would have gone looking for problems that
no longer existed. If you are reading this and the facts below do not match the
tree, trust the tree and correct this — a half-true review costs more than no
review._

### Open

**1. `main.py` still holds the login and OAuth flows.** At 1,865 lines it is no
longer the monolith it was (3,701 in September, 1,986 when first flagged in
June): the `/admin` pages moved to `admin/`, the platform API to `platforms/`,
and the dashboard was already in `dashboard/`. What remains is app construction
— which belongs there — plus the login/OAuth routes and about 590 lines of
`/admin` pages that share page-rendering helpers with each other. Moving those
means moving the helpers first, which is a refactor rather than a relocation.

**2. `dashboard_settings.py` has not moved into the `dashboard/` package.** It
still references renderer internals through compatibility aliases.

**3. Files are stored as Postgres `BYTEA`.** `client_insight_documents` keeps
raw file content in the database, which bloats it and gives vacuum more work
than it needs. An object store is the right home. File retrieval also reads
whole documents into memory rather than streaming.

**4. Auth-path test coverage is thin.** `oauth_flows.py` is at 36% and
`web_users.py` at 37% — the least-covered code in the repo handles tokens and
sessions. The security-critical primitives in `oauth_flows` (the post-login
redirect check, the connect-link token, the OAuth state) are now covered; the
provider-specific code exchanges are not. Writing the first batch found a live
open redirect, which is the argument for continuing.

**5. Content-Security-Policy cannot set `script-src` or `style-src`.** 83
inline `style` attributes reach the DOM — 47 written into the served markup and
36 more inside HTML the cached script builds and assigns via `innerHTML` — and
each dashboard page emits a small inline `<script>` carrying its per-request
configuration. All of those are blocked by the respective directive without
`'unsafe-inline'`, so the strongest XSS control available stays switched off
until they are gone or a per-request nonce is threaded through.

(The 22 `element.style.<prop> = …` assignments in the script are *not* a
problem: CSP does not restrict the CSSOM, only styles parsed from markup. Worth
knowing before anyone tries to convert them.)

**6. Most environment variables are undocumented.** The app reads about 110;
`.env.example` describes 29 of them, and the omissions include `DATABASE_URL`,
`DB_POOL_ENABLED`, the cache TTLs and every `BQ_*` routing value. Standing the
app up from the repository alone is not currently possible.

**7. Connection pooling is built but opt-in.** `db.py` funnels every read and
write through one pooled helper and 239 call sites use it, but
`DB_POOL_ENABLED` defaults off. Unless it is set in Railway, each of those call
sites still opens a TCP connection per query.

**8. Style-only lint rules are deferred.** `pyproject.toml` records which and
why: import sorting (~97 files) and flake8-simplify (~107 sites) would each be a
large mechanical diff, and three smaller rules still have findings.

### Closed since the June review

| Debt as recorded in June | What is true now |
|---|---|
| No connection pooling | `db.py` pools; 239 call sites migrated (flag still off — see 7 above) |
| No migrations framework | `db_migrate.py`, plus a CI guard keeping DDL off read/write paths |
| Redis declared but unused | Gone from `requirements.txt` |
| Only one test file | 130 files, ~1,600 tests, ~25s in CI |
| `models.py` has 650+ classes | 573 lines, 62 classes |
| Penn hardcoded throughout | One `penn_*.py` module, three `PENN_*` variables |
| Checked-in OpenAPI artifacts | None in the tree |
| `main.py` monolith | 3,701 → 1,865 lines (see 1 above) |
| No observability on failures | Logging is configured; 103 silently-swallowed exceptions now log or explain why not |

## Areas of Risk

### Open

**1. Rotating `OAUTH_TOKEN_ENCRYPTION_KEY` invalidates stored tokens.** Tokens
are encrypted at rest with a key derived from that variable and there is no
key-versioning or re-encryption path, so rotating it silently breaks every
stored connector until each is reconnected by hand.

**2. Rate limiting depends on the database.** `login_rate_limit` keeps its
buckets in Postgres. If the database is unreachable the limiter fails open, so
the login endpoint loses its throttle exactly when the system is least healthy.

**3. No alerting on sync failure.** A platform sync that fails now leaves a log
line, which is new — but nothing watches for it, so a connector can stop
producing data and the first report of it will come from whoever notices the
dashboard is stale.

**4. External API calls have no general retry or breaker.** GTM is the exception
and shows the pattern worth copying (`gtm_quota`: a shared token bucket and a
breaker that trips on a real rejection). The other platforms retry ad hoc or not
at all.

**5. Penn-specific sync entrypoint.** `refresh_penn()` is still the shape the
cron worker drives, so adding cron-driven sync for another client needs code
rather than configuration.

### Closed since the June review

| Risk as recorded in June | What is true now |
|---|---|
| Endpoints open when `API_KEY` is unset | Startup refuses to boot in production without it |
| Shared secret fallback chain | Resolved before the June review was written |
| No CSRF protection | Resolved before the June review was written |
| Synchronous DB blocking the event loop | 19 handlers, including the whole auth dependency chain, now run in a threadpool |
| BigQuery SQL injection surface | 174 typed query parameters; interpolated values are dates or allowlisted keys. `_resolve_stage()` documents why its interpolation is safe. No injectable path found |
| `/health` is static | `/health/ready` verifies database connectivity |
| Open redirect after login | Fixed: `validate_return_to` now refuses backslash and control-character bypasses as well as `//` |
